## 8. ID / Naming / Time Conventions

**ID Strategy:** BIGINT AUTO_INCREMENT for all tables. Rationale: ~500 users, single instance, no distributed-write requirement. Future opaque public ID is optional future consideration.

**Naming:** snake_case tables and columns; PK `id`; FK `<ref>_id`; constraint names deterministic.

**Timestamps:** `DATETIME(3)` UTC for instants; `DATE` for business dates. No timezone hardcoded. Business timezone `Asia/Ho_Chi_Minh` is Spring app config.

## 10. Identity / Auth Schema

- `accounts`: username/password_hash/role/display_name; no plaintext password; no JWT table.
- `invitations`: code_hash (bearer credential hashed); org_unit_id; single-use; lifecycle column; atomic consumption designed.
- Session: no persistent session table — ADR-004 server-managed in-memory session.
- No refresh/access token tables.

---

## 11. User / Organization Schema

- `org_units`: fixed 3-level hierarchy (DAI_DOI/TRUNG_DOI/TIEU_DOI) via CHECK + application enforcement.
- `user_assignments`: one current Tiểu đội per user (UQ on account_id).
- `user_assignment_history`: append-only; effective_from/effective_to; overlap prevention via transaction.
- `positions`, `ranks`, `user_classifications`: Admin-configurable lookup tables (ADM-003).

---

## 12. Invitation Schema

- `code_hash` instead of raw code — security decision for bearer credential.
- `org_unit_id` scoped to TIEU_DOI (application-enforced type check).
- `status` IN ('ACTIVE','CONSUMED','DISABLED','EXPIRED').
- `consumed_by_account_id` + `consumed_at` for audit trail.
- Atomic consumption: SELECT FOR UPDATE + single transaction.

---

## 13. Content / File Schemas

- Each content module has domain-owned category table: `handbook_categories`, `news_categories`, `music_categories`.
- No shared global category table (preserves module ownership and FK integrity).
- `file_metadata` owned by `file` module; referenced by content modules via FK.
- Binary files outside MySQL; `storage_key` is logical key.
- `publish_status` VARCHAR CHECK ('DRAFT','PUBLISHED') on content tables.

---

## 14. Quiz Schema

- **Historical correctness strategy: B — Immutable attempt snapshot.**
- `quiz_attempt_questions` captures question text at attempt creation.
- `quiz_attempt_answers` stores option text snapshot and graded flag.
- `quiz_config_snapshot` captures config at attempt start.
- `is_correct` on options never sent to client before reveal.
- `quiz_results.raw_score` stored internally; not exposed to USER.
- `is_competition_eligible` flag controls competition source eligibility.

---

## 15. Weekly Schema

- `weekly_questions(period_year, period_week)` UQ enforces one question per ISO week.
- `period_status` ('OPEN','CLOSED') governs submission acceptance and reveal.
- `weekly_submissions` UQ on (account_id, weekly_question_id) enforces one submission.
- `correct_explanation` revealed only after period closes (application-enforced).
- Late submission rejected: application checks `period_status = 'OPEN'` before accepting.

---

## 16. Political Education / Quiz Association

- `edu_lecture_quiz_ref` table with UQ on `lecture_id` enforces 0..1 Quiz per Lecture.
- Cross-module FK: `edu_lecture_quiz_ref.quiz_config_id → quiz_configs.id`.
- This is a valid relational FK. Application access still only through public Quiz capability (V0.3 module boundary rule).
- EDU owns: `edu_programs`, `edu_topics`, `edu_lectures`, `edu_documents`, `edu_lecture_quiz_ref`.
- Quiz owns: all quiz_ tables. No duplicate assessment engine in EDU.

---

## 17. Competition Schema

- `comp_policies` / `comp_criteria`: Admin-configurable per BD-V04-002.
- `comp_contributions`: dedicated nullable FKs per source type (quiz_result_id, weekly_submission_id, manual_adjustment_id) — preserves referential integrity vs weak polymorphic design.
- `comp_manual_adjustments`: Admin actor recorded; reason required; period scoped.
- `comp_corrections`: authorized correction path for closed periods.
- `comp_individual_outcomes`: UQ (period_id, account_id); computed snapshot.
- `comp_unit_outcomes`: UQ (period_id, org_unit_id); snapshots eligible_member_count for closed-period stability.
- Historical attribution: `user_assignment_history` queried to determine eligibility at period time.

---

## 18. Popular Content / Reporting Schema

- `popular_view_daily`: one row per (content_domain, content_id, view_date).
- Atomic increment via `INSERT ... ON DUPLICATE KEY UPDATE view_count = view_count + 1`.
- Aggregation for week/month/year: `SUM(view_count)` filtered by date range.
- No personal view history stored. No viewer identity.
- `content_id` has no FK (cross-module; orphan risk documented; dashboard handles LEFT JOIN).
- Included domains: HANDBOOK, RESOLUTION, NEWS, EDU, HCM.
- Excluded: QUIZ, WEEKLY, COMPETITION, ADMIN, AUTH, MUSIC.

## 20. Constraint Strategy

- All FK relationships documented with ON DELETE action (RESTRICT / CASCADE / SET NULL).
- Historical facts (attempts, results, submissions, contributions, assignment history): RESTRICT — never cascade-delete.
- Optional refs (thumbnails, author): SET NULL — content survives file/author deletion.
- Hierarchy cascade: UPDATE CASCADE for ID column changes (rare; IDs are PK and stable).
- Application-enforced constraints documented: org hierarchy types, invitation org type, one-active-attempt, assignment overlap, source type single FK.

---

## 21. Index Strategy

- 37 indexes defined (including UQ indexes).
- Every index has stated supporting query/use case.
- Indexes not created for every FK column — only where query evidence exists.
- FULLTEXT index on `handbook_articles(title, body)` as candidate (marked with Vietnamese tokenization risk).
- No speculative indexes.

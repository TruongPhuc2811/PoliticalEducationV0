## 7. Existing architecture analysis

- Backend root is `vn.pes`, Java 21/Spring Boot 4.1.0 with MVC, Security, JPA, Validation, Flyway, MySQL, Actuator and OpenAPI dependencies.
- Exactly 14 package boundaries exist as placeholders. No business implementation/entity/repository/query exists.
- `SecurityConfig` currently permits health/OpenAPI/ping, requires authentication elsewhere, and enables form login + HTTP Basic. This is skeleton behavior, not final auth design.
- Base config uses OSIV false, Flyway enabled and `ddl-auto=validate`; base profile defaults to `dev`.
- Dev/test/prod use MySQL; prod DB/storage values come from environment. Migration folder deliberately has no business SQL.
- Frontend client sends `credentials: include`, supporting but not approving the same-origin session candidate.
- No Nginx production config/server details exist; runtime production remains unverified and `OI-003` remains open.

## 8. System-context design

PASS. Actors User/Chiến sĩ, Admin, Super Admin and Browser are separated from React/Nginx/Spring Boot/MySQL/file storage. External news/media are optional boundaries, not invented services. Mermaid context diagram is included.

## 9. Runtime architecture

PASS. Browser → HTTPS/Nginx → React static + `/api` proxy → Spring Boot → MySQL/local storage is explicit. SPA fallback, health, static caching concept, process lifecycle, filesystem permissions and dependency behavior are described without final Nginx/server config.

## 10. Modular Monolith design

PASS. Package-by-feature, one-way public application boundaries, no cross-module repository access, no entity leakage, narrow `common`, proportional logical layers and circular-dependency prevention are normative.

## 11. Module inventory

Exactly 14 unique boundaries:

`auth`, `user`, `handbook`, `resolution`, `news`, `music`, `quiz`, `politicaleducation`, `hochiminh`, `weeklyquestion`, `competition`, `file`, `dashboard`, `common`.

Each row records responsibility/ownership, public capability, allowed/prohibited dependencies, Requirement/UC groups and OI impact. No physical database model is present.

## 12. Dependency/transaction rules

- Controllers map HTTP; application use cases own orchestration/authorization/transactions; domain owns approved invariants; infrastructure owns adapters.
- Cross-module use goes through application/query capabilities.
- Read-only transaction is permitted when appropriate.
- DB transaction is not held across file streaming/external network/long export.
- Registration/submission/publication/file coordination are concurrency-sensitive; no isolation/lock algorithm is invented before policy/data design.

## 13. Authentication/security design

`TD-001` is Proposed: Spring Security + server-managed browser session + HttpOnly cookie for same-origin Nginx deployment. Rationale uses current deployment direction and `credentials: include`; alternatives JWT/opaque token and tradeoffs are recorded. Current form/basic skeleton is explicitly non-final.

Password hashing, HTTPS, cookie Secure/HttpOnly/SameSite, fixation protection, CSRF and safe error/logging expectations are defined. Password policy/reset/lockout remain Deferred. `OI-006` blocks invitation lifecycle and final auth API/DB implementation.

## 14. REST/API conventions

PASS. Proposed `/api/v1`, resource naming, method semantics, status principles, camelCase JSON, timezone, OpenAPI, bounded server pagination/filter/sort and idempotency/conflict principles are defined as V0.3 proposal, not endpoint inventory.

## 15. Error/validation model

PASS. Spring `ProblemDetail` is preferred with safe status/code/title/detail/fieldErrors/requestId semantics. Web DTO validation and application/domain validation are separated; stack/SQL/path/secret leakage is forbidden. HTTP states map to V0.5 UI patterns.

## 16. File/storage design

PASS. `StorageService` conceptual store/open/read/delete/metadata operations, generated storage identity, original display name, local V1 adapter and future S3-compatible adapter are defined. Binary remains outside MySQL. Upload sequence and failure cleanup are documented without schema/API implementation.

## 17. External integration design

- News: provider port + normalization boundary; Admin-authored content remains independent; no provider/RSS/API/crawler/scheduler chosen (`OI-001`).
- Music: local file metadata vs YouTube link/embed; no YouTube API/proxy/download/autoplay.
- Optional external failure does not cascade into stored/internal content flows.

## 18. Quiz/Weekly/EDU boundaries

- Quiz separates Question Bank, configuration, attempt, submission, grading and result. Server grades; client never gets answers/bank early. `OI-007..OI-009` and `OI-002` block lifecycle/ranking/competition behavior.
- Weekly owns configure/current/submit/grade/reveal, with `OI-010` preserving all lifecycle decisions; no scheduler assumed.
- Political Education preserves Program → Topic → Lecture → Document → Test and presents two test-integration possibilities without choosing one (`OI-011`). No progress/completion is invented (`OI-012`).

## 19. Competition/reporting boundaries

- Competition owns approved input/calculation/read model after policy approval; source facts come through explicit capabilities, never repository reach-through.
- A score/input ledger is only a Domain Candidate.
- Dashboard/reporting owns query aggregation/on-demand export; widget failure isolation and no polling are baseline.
- `OI-002`, `OI-012`, `OI-014` and `OI-013` remain blockers.

## 20. Data ownership

Logical ownership is explicit for credentials/account/content/result/storage/reporting. Cross-module writes have one application owner. Physical relationships/delete/constraint behavior are deferred to V0.4.

## 21. DB/Flyway boundary

MySQL 8.4, JPA/Hibernate, Flyway-only schema evolution, `ddl-auto=validate`, dedicated MySQL test DB, no H2 substitution and no Testcontainers are retained. Pagination/bounded queries and implementation-time N+1/fetch review are required. No schema DDL, SQL migration, key/index or JPA model is created.

## 22. Config/profiles/deployment

Dev/test/prod responsibilities and environment wiring are documented. Known risk is explicit:

> Production process MUST explicitly set `SPRING_PROFILES_ACTIVE=prod`.

Nginx serves SPA/proxies `/api`; process manager is `TD-002`; production host/domain/TLS/limits remain `OI-003`/`OI-005`. Task does not change runtime config.

## 23. Security threat review

Design review covers credential brute force/enumeration, unauthorized Admin, CSRF, XSS/rich content, upload abuse, traversal/symlink, filename/MIME, IDOR, mass assignment, SQL injection/unsafe sort, leakage, oversized request/export and external provider/embed risks. Each row has mitigation and remaining decision; no penetration-test claim.

## 24. Resource/performance considerations

Baseline is a simple Modular Monolith with bounded/paginated queries, projections, streaming files/exports and on-demand reporting. No load-all, media BLOB, polling, unnecessary scheduler/cache/broker/thread pool. Anti-patterns include N+1, EAGER collections, query-in-loop, unbounded/in-memory filtering, whole-file reads, excessive logs and busy retry loops.

There is no query/business workload implementation to measure N+1/full scan/CPU/RAM.

## 25. Failure modes

Expected safe degradation is defined for MySQL/storage/external news/external media/session/validation/missing file/export/widget failure. Optional integration does not cascade; no retry framework is added.
